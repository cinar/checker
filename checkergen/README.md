# Checkergen

`checkergen` generates reflection-free Go validation code from [Checker](https://github.com/cinar/checker)'s `checkers` (and `validate` fallback) struct tags. For an eligible struct, it emits a `Check<Type>(v *Type) (checker.CheckErrors, bool)` function that calls the same checker/normalizer functions `CheckStruct` would run through reflection — but resolved and called directly at compile time via [`checker.Check`](https://pkg.go.dev/github.com/cinar/checker/v2#Check), instead of walking the struct's fields with `reflect` at runtime.

`checkergen` and `CheckStruct` are meant to coexist. Generate code for the structs on your hot paths; leave everything else on `CheckStruct`. A struct with a field outside `checkergen`'s scope (see below) is skipped with a clear reason, not generated incorrectly.

## Why

Every checker/normalizer already has a plain, non-reflection Go function alongside the `reflect.Value`-based one `CheckStruct` uses internally — `Required[T](value T)`, `IsEmail(value string)`, `MinLen[T](n int) CheckFunc[T]`, and so on. `checkergen`'s job is mostly templating: read a struct's tags, and emit a call to the right one, in order, via `checker.Check`:

```golang
type SignupRequest struct {
	Email    string `json:"email" checkers:"trim lower required email"`
	Password string `json:"password" checkers:"required min-len:8"`
}
```

generates:

```golang
// Code generated by checkergen. DO NOT EDIT.

func CheckSignupRequest(v *SignupRequest) (checker.CheckErrors, bool) {
	errs := make(checker.CheckErrors)

	{
		newValue, err := checker.Check(v.Email, checker.TrimSpace, checker.Lower, checker.Required, checker.IsEmail)
		v.Email = newValue
		if err != nil {
			errs["email"] = err
		}
	}

	{
		newValue, err := checker.Check(v.Password, checker.Required, checker.MinLen[string](8))
		v.Password = newValue
		if err != nil {
			errs["password"] = err
		}
	}

	return errs, len(errs) == 0
}
```

No reflection at runtime — every call is resolved and type-checked at compile time.

### Performance

Benchmarked against the equivalent `CheckStruct` call, on the same struct and input, in this module's own `checkergen` package:

| Struct | `CheckStruct` | Generated | Speedup |
| :--- | ---: | ---: | :---: |
| 5-field signup form | 1830 ns/op, 1304 B/op, 24 allocs/op | 562 ns/op, 168 B/op, 7 allocs/op | **~3.3x faster, ~8x less memory** |
| 25-field mixed checker coverage | 8200 ns/op, 4928 B/op, 59 allocs/op | 2730 ns/op, 760 B/op, 9 allocs/op | **~3.0x faster, ~6.5x less memory** |

Run `go test -bench . -benchmem ./checkergen` from the repository root to reproduce.

## Install

```bash
go get github.com/cinar/checker/v2/checkergen
```

## Usage

Add a `//go:generate` directive to the package containing the struct(s) to generate for, then run `go generate`:

```golang
//go:generate go run github.com/cinar/checker/v2/checkergen/cmd/checkergen

type SignupRequest struct {
	Email    string `json:"email" checkers:"trim lower required email"`
	Password string `json:"password" checkers:"required min-len:8"`
}
```

```bash
go generate ./...
```

This scans the current package for every struct with at least one `checkers`/`validate`-tagged field and writes `checkergen_generated.go`, containing a `Check<Type>` function for each one it could generate. Restrict generation to specific structs with `-type`:

```bash
go run github.com/cinar/checker/v2/checkergen/cmd/checkergen -type=SignupRequest,LoginRequest
```

A struct it can't generate for is skipped, with the reason printed to stderr — it isn't written as broken code, and doesn't stop the rest of the package's structs from being generated.

## Scope

A struct field is only eligible for generation if its Go type is exactly one of the predeclared scalar types: `string`, `bool`, or one of the `int`/`uint`/`float` kinds. Not eligible, for now:

- A named/defined type (`type Email string`) — the reflect-based path handles these for free via `reflect.Value.String()`; static codegen would need explicit conversions this version doesn't generate yet.
- A pointer field.
- A nested struct, slice, or map field.

Every checker and normalizer with a plain, non-reflection function is supported; a checker without one (including a custom one registered only via `checker.RegisterMaker` at runtime, which `checkergen` can't see at generate time) fails generation for that struct with a clear diagnostic rather than silently producing incomplete validation.

Two checkers behave slightly differently from `CheckStruct`, both deliberately:

- `eq-field` compares with `==` (`comparable`) via the generated code's `IsEqField`, instead of the `reflect.DeepEqual` the `eq-field` struct tag uses at runtime through `CheckStruct` — matching how every other comparison checker (`IsEq`, `IsGte`, ...) already works. This only differs in practice for a slice/map/struct-typed field, which isn't eligible for generation in the first place.
- `eq`, `ne`, and `oneof` support any field type via `checkergen`'s generated call to the fully generic `IsEq`/`IsNe`/`IsOneOf`, even though the `checkers`-tag path through `CheckStruct` currently only supports a string field for these three (their reflect-based implementation hardcodes a string conversion). Generated code is a strict capability superset here, not a behavior change for anything `CheckStruct` already validates correctly.

## What Building This Found

Every bug below was caught before merge, by generating real code from real struct tags and diffing its behavior against `CheckStruct` for the same input — not by reading the generator's source and reasoning about it.

- **A field-name bug in the generated `eq-field` closure.** The first draft used the sibling field's *json*-tag name for the error message (`errs["confirmPassword"] = ...` reporting `field: "password"`) instead of the field name exactly as written in the tag (`field: "Password"`) — what `CheckStruct`/`IsEqField` actually puts there. A `{{ .field }}` placeholder in a translated error message would have silently shown the wrong name in every non-English locale. Caught by the differential test comparing generated output field-for-field against `CheckStruct`'s.
- **A malformed tag could crash generation for an entire package.** `after-field:DateOnly` (missing the `:field` half) panics at generate time, exactly like the equivalent runtime `after-field` maker panics on the same malformed tag — but an unrecovered panic during `Generate` took down the whole run, not just the one struct. Fixed with the same panic-recovery pattern the `cli` module already uses for `CheckWithConfig` (see the root `CLAUDE.md`): one struct's bad tag is now a skip with a diagnostic, not a crash for every other struct in the package.
- **`eq`, `ne`, and `oneof` are string-only today, even on a numeric field — in the core library, not just here.** Building the differential-test fixtures, `checker.CheckStruct` panicked with `string expected` on a field like `Priority int checkers:"eq:1"`. `checkEq`/`checkNe`/`checkOneOf` — the reflect-based functions the `eq`/`ne`/`oneof` struct tags actually run through — hardcode a `reflectString` conversion, even though the exported `IsEq`/`IsNe`/`IsOneOf` are fully generic. This is a pre-existing limitation in the core module, not something `checkergen` introduced: `checkergen`'s generated code for these three checkers calls the generic functions directly, so it validates strictly more than the `checkers`-tag path can today (see [Scope](#scope) above). Worth fixing at the source; documented here as a known divergence until then.
